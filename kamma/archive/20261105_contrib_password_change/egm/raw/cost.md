## Cost / capacity review — 20261105_contrib_password_change

**Blocker — nothing caps the new resident process, and the unit precedent has no limits.** `scripts/server_contrib/dpd-gui@.service:1-30` sets no `MemoryMax`/`MemoryHigh`/`CPUQuota`. At 01:00 `maintenance_window.py` stops only `--instance` units (`_systemctl("stop", ...)`, maintenance_window.py:412) and then runs `db_rebuild_from_tsv.py` (line 145); runbook Step 3a states the build "uses almost all memory… do not build without swap" (4 GB swapfile, 8 GB RAM). A password service with unlimited RSS is the one process still resident at that moment. Fix: ship its unit with `MemoryMax=128M`, `MemoryHigh=96M`, `CPUQuota=20%`, `Restart=on-failure`.

**Blocker — the hash cost the new service writes is unspecified, and the natural default is 128× the existing one.** `add_contributor.sh:84` runs `htpasswd -B -c` with no `-C`, i.e. apache's default cost 5. The brief pins only the *verify* side (`htpasswd -vb`); the write side is open, and Python `bcrypt`/`passlib` default to 12. nginx re-reads `auth_basic_user_file` and recomputes bcrypt on every authenticated HTTP request, not once per login — and a Flet page load is dozens of requests. cost 12 is 2^7 = 128× cost 5: one contributor's page load becomes tens of seconds of a core, on 2 vCPU, at the same time as the rebuild. Fix: pin the same cost 5 (`htpasswd -B -C 5`), and measure `/user/` first-paint before and after.

**Blocker — architecture fork 1 (shared unauthenticated page) creates a public bcrypt oracle with zero throttle.** Neither `nginx_contrib.conf.template` (entire file) nor `nginx_contrib_user.conf.template` (entire file) contains `limit_req_zone`, `limit_req`, or a cache; runbook Step 3b's package list installs no fail2ban. An attacker then picks the rate: at cost 5, thousands of guesses/sec at negligible cost; at any higher cost, both vCPUs pinned and every contributor's latency collapses. Fork 2 (per-user basic auth first) removes the anonymous path; either way add `limit_req_zone $binary_remote_addr zone=pw:1m rate=5r/m` plus a per-username attempt counter. Token economics tie-in: the same host holds `config.ini` with the DeepSeek/OpenRouter keys (runbook Step 4), so an anonymous 443 code path shares a blast radius with paid API quota.

**Major — verify-by-subprocess is an unstated per-request cost.** `bcrypt` is not a dependency (`pyproject.toml` dependencies list has fastapi/uvicorn, no bcrypt), so each verify forks `htpasswd` (~10–20 MB, ~10 ms). Fine at five contributors, but it multiplies exactly in the load case of the finding above, and a synchronous verify inside `async def` serializes on uvicorn's single worker. Fix: `await asyncio.to_thread(...)`, and state an expected contributor ceiling — the brief and `spec.md` contain no number at all.

**Major — startup shape.** `ExecStart=@UV@ run --no-sync python gui2/main.py` (dpd-gui@.service:20) means two processes per instance; copying it adds uv's ~40 MB. Worse, any import from `db/` or `gui2/` (or `tools.printer`) drags SQLAlchemy/rich/flet into a resident process for a 2 KB job. Fix: ExecStart `.venv/bin/uvicorn ... --workers 1`; spec line "stdlib + fastapi/uvicorn only, nothing from `db.`". Related: `os.replace` gives the file the *temp file's* mode/owner, so a 644 temp exposes the hash and root:root makes nginx answer 500 for that user (runbook Step 7a expects `640 root:www-data`) — set mode/group on the temp before replacing.

**Nit — the memory-cut premise is unverifiable here.** No source records what the two 20261102 cuts saved or the current headroom; `spec.md` is a placeholder with no peak-load figure. Have the plan record `free -m`, `systemctl show -p MemoryCurrent dpd-gui@alice`, and peak during one rebuild, then size the new process from that.
