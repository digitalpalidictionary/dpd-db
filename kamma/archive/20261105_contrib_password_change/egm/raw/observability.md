## Findings — observability lens

**1. Blocker — the new service has no supervision or log surface at all.** The brief defines forks 1–4 but never names a unit, log destination, restart policy or health endpoint. Contrast `scripts/server_contrib/dpd-gui@.service:19-22` (`Restart=on-failure`, `RestartSec=10`, `TimeoutStopSec=30`) and `scripts/server_contrib/README.md` ("Logs: `journalctl -u dpd-gui@<user>`"). Failure scenario: the app is OOM-killed or crashes on an unhandled exception (8 GB box, swap pressure documented in the README); every `POST /password/` then answers 502, contributors report "the change failed", and the maintainer has no unit to query, no status line, no restart. `/status` (`nginx_status.conf.template:8`) keeps reporting the last *maintenance* outcome, so nothing looks wrong. Fix: ship `dpd-password.service` beside the gui2 unit with `Restart=always`, `RestartSec=5`, `MemoryMax`, a `/health` route, and a runbook CHECK (`systemctl is-active`, `curl -o /dev/null -w '%{http_code}' http://127.0.0.1:<port>/health`).

**2. Blocker — a successful change can lock the user out while reporting success.** `os.replace` gives the target the *temp* file's mode and group. `add_contributor.sh:69` sets `umask 077` before creating the htpasswd and then explicitly `chmod 640` + `chgrp` nginx's group (lines 70-93). A rewrite that omits both yields `600 root:root` → nginx cannot read the file → **every** request for that user is 500, yet the app returned 200 and wrote "changed". Fix: after replace, re-assert mode 640 and the nginx group, then re-verify the new hash by stdin; on any failure log ERROR and return 500 so the user knows the password did *not* change. Record the outcome line.

**3. Major — no audit trail, so brute-force and disputed changes are untraceable.** `contrib_pull.py` redacts secrets into `logs/contrib_pull_status.txt` + `logs/contrib_pull.log`; `maintenance_window.py:231-296` reads its own log to build `/status`. The password design specifies no equivalent. Without per-attempt records the maintainer cannot answer "was alice's account attacked?", "did alice really change it on Tuesday?", or "how many 401s before the lockout". Fix: append-only `/var/log/dpd/password.log` (0600 root, logrotate) with `ts user ip outcome` per attempt — never the password. Cheap, greppable, survives reboot (journald `Storage=auto` may be volatile — verify `/var/log/journal` exists on the host).

**4. Major — source IP is not forwarded, so any throttle or attempt log reads 127.0.0.1.** `nginx_contrib_user.conf.template:14-17` sets only `Host`, `Upgrade`, `Connection`. If the new location copies that pattern, every log line and rate-limit bucket is the proxy address: one attacker saturates the shared bucket and locks out everyone, and triage cannot tell a local Flet session from an external attempt. Fix: add `X-Forwarded-For`/`X-Real-IP` in the new location; the app trusts them only from loopback and logs them.

**5. Major — `/status` cannot absorb a second writer.** `_write_status` rewrites the whole `status.txt` with temp+replace (`maintenance_window.py:265-270`). A password service appending to the same file is silently clobbered each 01:00 run. Fix: its own file (`/var/lib/dpd/status_password.txt`) behind its own `location`, one writer per file.

**6. Major — the password lands in `argv` if `htpasswd -vb <file> <user> <password>` is used.** The brief names that CLI form; the runbook forbids it twice (`NEW_SERVER_RUNBOOK.md`, rule 1 and Step 11: "Do not put a password in a command text"). `ps`/auditd/journal-capture then holds the secret. Fix: pass it on stdin (`-i`), and verify `-vbi` actually accepts stdin before relying on it; otherwise compare the hash in-process.

**7. Nit — temp filename and the nginx include glob.** `nginx_contrib.conf.template:11` does `include /etc/nginx/dpd/*.conf`; a crashed write leaving a `*.conf`-shaped temp file inside that directory makes the next `nginx -t`/reload fail for **all** contributors. Use a dot-prefixed temp name outside the glob and sweep stale temps at startup.

**8. Nit — triage is undocumented.** No runbook step, so nobody knows that 401 = wrong password, 500 = group/permission (finding 2), 404 = no such user, 502 = dead service. Write that matrix into `NEW_SERVER_RUNBOOK.md` as a Step 11 CHECK before shipping.
