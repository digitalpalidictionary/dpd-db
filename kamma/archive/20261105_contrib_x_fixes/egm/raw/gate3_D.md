**Major — 13.3 `_steps` edit contradicts the helper's real shape.**
`tests/scripts/server_contrib/test_maintenance_window.py:80-87` already iterates `**overrides` with `setattr(steps, name, value)`. Adding `translation_db=lambda config: None,` *inside* the `WindowSteps(...)` call (as the plan says) also forces adding the field to the dataclass — fine, but the plan then makes `_steps(calls, translation_db=...)` in the new tests work through `overrides`, which it already does. Net: the "add one argument" instruction is redundant and, read literally, the executor will put the no-op inside the constructor **after** `health_check=...` while `overrides` still applies — two different mechanisms for one field. Say plainly: "add `translation_db=lambda c: None` to the `WindowSteps(...)` call" OR "the helpers already take overrides; add it only to the constructor". Same issue in `test_round_trip.py:52-60`.

**Major — 13.3 new test's second run depends on unverified log/status plumbing.**
`test_a_failure_is_logged_and_the_window_goes_on` asserts `outcome is Outcome.REBUILT`, `"rebuild" in calls.names` and `"translation db missing (window goes on): no network" in setup.log_text()`. `Setup.log_text` (test_maintenance_window.py:37-40) reads `glob("maintenance_*.log")[0]` — the *first* log file, not necessarily this run's; if any other test in the file wrote a log for a different date, or if the day matches, OK; but the test does not create the failure on a fresh `Setup`, and `_write_status` (`maintenance_window.py:180-190`) copies every ERROR line of the day's log into `status.txt`. So the status assert would pass even if the *translation db* line were absent, as long as any earlier ERROR is present. The plan never tells the executor that. Fix: assert on the exact line only, or scope the log read.

**Major — 13.4 `_run` signature and cwd: plan names `config.project_root` but the failure path is what the test asserts; no error strategy specified for the return code.** `ensure_translation_db.main()` returns 1 rather than raising, so `_run(..., check=True)` (`maintenance_window.py:108`) will **not** raise on a missing db. The window's log then says `translation db present` even when it printed "missing". Test `test_a_failure_is_logged...` only passes because it injects a raising stub — the real default step is silently wrong. Spec 14 (spec.md:92) wants failure logged. Fix: `_default_translation_db` must check the return code (`subprocess.run(..., check=True)` won't; use `subprocess.run` + `raise RuntimeError`) — the plan must say so, otherwise the executor follows it literally and ships the bug.
