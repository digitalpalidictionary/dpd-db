## Findings

**Blocker — #8 is based on a false premise, and its "after a good run only" rule breaks rollback safety.**
`scripts/server_contrib/maintenance_window.py:286-289` writes `dpd.db.prev` on *every* run that gets past the dirty check, and `:309-316` reads it back on failure. It is the rollback copy, not a leftover. The brief itself admits "owner's note; not read in code this session" (`egm/brief.md:35`). Deleting it "after a good run only" is fine, but only if deletion happens after `_restore_rollback` can never fire — i.e. in the `finally` after `outcome == REBUILT`, not in the success path inside the `try`. Any tidy-up placed at `:429` (`last_built.write_text`) will also delete the backup when `_restore_build_changes` or `_apply_wal` later fails, leaving nothing to roll back to. Also note the worktree: `_contrib_worktree` is supplied by `--worktree` and used by `push_contributions` (`:98-101`); nothing in this module creates or removes it, so "delete `_contrib_worktree/`" targets a path owned by `contrib_push.py`. Fix: verify who creates the worktree first (grep returned no creator in `scripts/server_contrib/`), then delete both artefacts only in the `try/finally` *after* the rebuild branch completes and `outcome` is `REBUILT`.

**Major — #7 contradicts the code's stated intent, and the "skip" notice will never fire on the path the owner means.**
`scripts/server_contrib/contrib_pull.py:596` already deliberately excludes skips: `if not args.dry_run and not status.outcome.startswith("skipped"):`. And `maybe_notify` (`:559-572`) only announces problems. Worse, both `skipped: editor open` returns (`:476`, `:526`) happen *before* `maybe_notify` is reachable in the `:526` case only via `run`'s return path; the `:476` case is inside `_pull`, whose `status` still flows to `:596`. So the fix is a one-character-class change at `:596`, not new code. YAGNI verdict: the notify-on-skip exists to warn "your pull did not happen" — but `skipped: already done today` and `skipped: another run` are equally silent and equally fine. Ask whether the owner wants *every* skip notified (then simplify `:596` to drop the filter entirely — less code) or only the editor-open one (then the special case is the smell). Do not add a third branch.

**Major — #4 and #12 are the same fix, done twice, and #4 is nearly a no-op after it.**
`gui2/main.py:746-747` calls `start_dpd_server()`; `tools/fast_api_utils.py:21-35` spawns uvicorn on `127.1.1.1:8080`. But `justfile:156-157` already provides `webapp` as the supported way to run that server, and `start_dpd_server` no-ops headless (`:25-26`). So today the only *live* effect of `start_dpd_server` on desktop is starting a uvicorn that nothing hits — because the consumer, `request_dpd_server`, is called only from `archive/` (confirmed: all call sites in `archive/gui/*.py`, plus the docstring claim at `:95-96` of the 20261023 spec). Removing `:746-747` is a 3-line deletion. But the tests (`tests/tools/test_fast_api_utils.py:17-43`, `tests/gui2/test_main.py:627,652`) monkeypatch it — removing it means deleting tests, not writing them. Fix: fold #4 into #12's "web version only" gate rather than keeping `fast_api_utils` alive for a caller that no longer exists; delete the module and its whole test file.

**Nit — #3 is already a solved problem.**
`gui2/database_manager.py:390-396` already wraps the save in `try/except Exception`, prints, and rolls back. "Quietly skip when read-only" needs a read-only probe (new detection logic) to suppress one print line. Deletion alternative: drop the `print` at `:395` and keep the `except`. Zero new code, no probe.

**Nit — #13 (flaky test) is not a "fix" and has no acceptance criterion.** The brief records 1 failure in 6 runs with cause not found (`egm/brief.md:36`). Investigating an unknown-cause flake inside a 13-item thread will consume the thread. `_write_status` (`maintenance_window.py:165`) reads the log file back by scanning for `"INFO maintenance window start"` and takes the *last* match from an append-only per-day log — a plausible race if two runs share a day. Ask the owner to split it out.

**Nit — #9 vs. #10 vs. #11 are UI/UX decisions, not defects.** `gui2/user.py:29,77-78` (`routed_username or "1"`, compared to `"1"`) is consistent as written; "agree when no username is set" needs a stated divergent scenario the brief never gives. #10 and #11 are preference changes with no failing behaviour cited.

**Not worth doing as scoped:** #4 (fold into #12), #3 (one-line print removal instead), #13 (split out), #9/#10/#11 (no defect stated).
