## Findings (UX + developer ergonomics)

**Blocker — Fix #7 contradicts the code it edits, and the notice would be redundant.** `maybe_notify` (`scripts/server_contrib/contrib_pull.py:559-571`) already announces any `pulled with problems` run at once, and its docstring says a skip is treated as the day's success. But `main()` gates the call at line 596: `if not args.dry_run and not status.outcome.startswith("skipped")`. Adding a second notify inside the two skip sites (476, 526) gives the maintainer duplicate or near-miss notices: a run naming a different skip reason ("another run", "already done today") stays silent, and `pulled with problems` already covers the editor-open case. Failure scenario: the maintainer gets two desktop pops for one problem, or none when the fixer assumes all skips are covered. Fix: change the line-596 guard and let `maybe_notify` own every announcement, so one function, one policy, one test.

**Major — Fix #10 greys out a button whose handler still shows the message, and the button isn't the only path.** `gui2/filter_component.py:174` builds `ft.Button("Save Changes", on_click=self._save_changes)` with no `disabled=self.read_only`, and `_save_changes` (426-431) still calls `show_global_snackbar(..., READ_ONLY_MESSAGE, "warning")`. Greying without removing the message leaves dead copy the contributor never sees, and the brief's "instead of showing a message" cannot be tested as written. Worse, `Ctrl+S` (`gui2/main.py:330-331`) calls `_on_save_changes` directly and bypasses widgets entirely — so a disabled button is cosmetic unless the keyboard path is gated too. Also Roots/Infl use `read_only` messages at three sites each (`roots_tab_view.py:294,343`; `inflection_templates_tab_view.py:789,844,881`) with `_set_message`, not snackbars — three different mechanisms for one rule.

**Major — Fix #11 cannot produce a starter preset by editing code.** It says "contributor starter preset is one filter, `lemma_1`". But the DB tab's defaults come from a per-user JSON file: `gui2/filter_tab_view.py:64` reads `get_first_preset()` from `filter_presets_manager.py:63`, and `gui2/paths.py:90` points that at `filter_presets_<username>.json`. On a fresh contributor the file is empty, so `get_first_preset()` returns `None` and the code falls through to the passed-in defaults (line 88-89). The work is: seed the file for contributors, or add a first-run default. As written, a contributor runs the task, sees no preset, and reports it as broken. Also state what happens to an existing editor's preset — overwriting it silently is a data loss.

**Major — Fix #12 needs a rule for the Alt+? popup.** `_shortcut_groups()` (`gui2/main.py:385-391`) derives the popup rows from `_TAB_JUMP_KEYS` and `_CLEAR_ACTIONS`. Turning Alt keys off in web but leaving the popup listing them gives contributors a help dialog full of dead keys — worse than no shortcut. Gate the popup and the keys off the same expression, and say so in the plan.

**Nit — Fix #3's "quietly" is untraceable.** The cache save is already inside a `try/except` printing `decon cache refresh failed`. "Skip it quietly" implies silence; that removes the only trace of a skipped refresh. Decide: silence, debug log, or keep the print. Say which, and why.

**Nit — Fix #1 has no contributor-visible message.** Wrapping `ft.Clipboard().set(...)` (`gui2/pass2_add_view.py`) stops the save breaking, but if nothing tells the user the copy failed they will paste the previous clipboard contents into an email and not notice. A one-line snackbar on the except branch costs nothing.

**Nit — Fix #8's destructive deletes deserve a dry-run line.** `maintenance_window.py:288` makes `dpd.db.prev` for rollback; deleting it "after a good run only" is right, but the status output should say what was deleted, so a maintainer reading the log knows the rollback copy is gone.

**Nit — the flaky test.** `test_status_file_reports_a_failure_and_its_reason` vs `problems: 0` smells like shared status-file state or a clock/`NOTICE_FROM` boundary (`contrib_pull.py:568`). The plan should name it as a hypothesis with a `tmp_path` isolation step, not "investigate".
