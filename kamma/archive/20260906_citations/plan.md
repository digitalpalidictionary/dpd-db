# Plan: How to cite DPD

## Architecture Decisions

- **`tools/version.py` builds the citation string.** It already generates the version and
  already writes the metadata block into `db_info`, so the citation belongs there. A new
  `make_citation(version)` returns the string; `make_db_metadata(version)` returns the
  whole block; `update_db_version` upserts it.
- **The existing `db_info` write only fired on first creation.** The old code added
  `author`, `license` etc. in the `else` branch, i.e. only when `dpd_release_version` was
  absent, so a key added later would never reach an existing database. Replaced with a
  real upsert. This also corrects `author` in databases that already hold the old value.
- **`update_db_version` now takes a `Path`, not `ProjectPaths`.** It only ever read
  `pth.dpd_db_path`, and the wider type made the function untestable without faking a
  whole `ProjectPaths`. One caller, in the same file.
- **DRIFT from the original plan — the offline citation is generated, not a TSV row.**
  The plan said add a row to `shared_data/reference/help.tsv`. That file is static text,
  so the entry could not name the version — and a citation without a version is exactly
  the thing this thread exists to fix. Instead `add_citation()` in
  `exporter/goldendict/export_help.py` builds the entry at export time from
  `make_citation()` and the version in `config.ini`, following the same shape as the
  existing `add_bibliography` / `add_thanks`. `help.tsv` is untouched.
- **DRIFT — the website now displays the version.** The plan only added a "how to cite"
  link. On inspection `dpd_release_version` reached the browser solely as a cache-busting
  query parameter and was shown nowhere, so a reader could not cite the version they were
  looking at. The footer now shows it next to the link.

- [x] Timing checked against the uposatha workflow. The local build and the GitHub
      release both derive the version from `year_month_day()`, and CI runs
      `tools/version.py` itself (`draft_release.yml`, "Create version"), so a local
      build and a same-day CI release produce an identical version string. The
      locally-generated page and CFF therefore match what ships.
      **Caveat:** if the CI run crosses midnight into the next day, CI's version will be
      a day later than the committed docs page. Not introduced by this thread — the
      release tag already came from the same source — but worth knowing.
      **DOI lag:** Zenodo only mints the concept DOI when it archives a release, which
      happens after the CI build. So the DOI is first picked up by the *following*
      month's build. One-off, by construction.

## Phase 7 — Zenodo handover

- [x] Checklist written (below), verified against Zenodo's current GitHub integration.
      → verify: steps match Zenodo's documented flow — connect account, toggle the
        repository, create a release, receive concept + version DOIs.

### Zenodo checklist for the user

1. Go to zenodo.org and log in with the GitHub account that owns `dpd-db`.
2. Open **GitHub** in the Zenodo account menu, find `digitalpalidictionary/dpd-db`, and
   switch it **on**. Zenodo only archives releases created *after* the switch.
3. Cut the next monthly release as usual.
4. Zenodo creates a record and issues two DOIs: one for that release, and a **concept
   DOI** that always resolves to the newest release. The concept DOI is the one to use.
5. The next build finds the DOI itself and stores it in `config.ini` under
   `[version] doi`, from where it flows into everything. To force it early, re-run
   `tools/version.py` then `just docs-update`. Do **not** hand-edit `CITATION.cff` or
   `docs/how_to_cite.md` — both are generated and would be overwritten.

Note: Zenodo caps a record at 50 GB. The release assets are far below that.
