## What happens on its own

1. The release build runs `tools/version.py`, which calls `ensure_doi()`.
2. `ensure_doi()` finds no DOI in config, queries Zenodo, and — on this first release —
   still finds nothing, because Zenodo archives the release **after** CI finishes.
   It prints `zenodo doi | not published yet` and carries on. **This is not a failure.**
3. Zenodo archives the release and mints the concept DOI.
4. The **next** build (October uposatha) finds it, writes it to `config.ini`, and from
   then on the DOI flows into the citation string, `db_info`, `CITATION.cff`, the docs
   page, the GoldenDict `cite` entry and the app card. Nothing further to do.

The one-build lag is by construction. It is not worth engineering around.

## If the Zenodo lookup misbehaves

`fetch_zenodo_doi()` searches for the quoted phrase `"digitalpalidictionary/dpd-db"` and
accepts a hit only if its `related_identifiers` point back at this GitHub repo AND the
DOI matches `10.xxxx/...`. A network or parse error is printed, not swallowed. Verify the
stored value anyway before trusting it:

```
grep -A1 "\[version\]" config.ini
```

It should read `10.5281/zenodo.<number>`. If it is wrong, the fix is to correct the
`doi` value in `config.ini`; nothing re-fetches once a value is present.
