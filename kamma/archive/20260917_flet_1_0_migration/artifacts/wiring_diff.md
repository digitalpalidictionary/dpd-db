### BR-14 — the removed binding

`gui2/main.py  ft.Tabs  on_click=self._on_tab_activated`

0.28 bound both `on_click` and `on_change` on the tab container, so every tab
activation fired `_on_tab_activated` **twice** — visible in the Phase 2c timing
log, where each activation appears once as `click` and once as `change`, and
absorbed at runtime by the `_mounted_tabs` dedup guard. 1.0 binds `on_change`
only. The single fire is therefore the preserved behaviour, not a lost handler.

The script treats this as an expected *removal* rather than a rename: if the
binding were still present it would report `EXPECTED TO BE REMOVED but still
bound` and fail. Absence is the pass condition.

### BR-8 — why the callable text changes, not just the keyword

1.0's `pop_dialog()` takes no argument: it closes whichever dialog is topmost,
where 0.28's `page.close(dlg)` named one. Every call site here closes the dialog
it just opened with nothing stacked above it, so behaviour is preserved — but
the argument could not be carried over, so the three lambdas read differently
in the inventory.

### BR-1 — the dropdown split, as predicted

The plan predicted this exact shape and it holds:

- **8 rows now bind `on_select`** — 7 direct `ft.Dropdown` sites
  (`compound_type_tab_view.py` ×2, `dpd_fields_family_set.py`,
  `filter_tab_view.py`, `pass1_add_view.py`, `pass2_add_view.py`,
  `roots_tab_view.py`) plus the `DpdDropdown` wrapper's own `super().__init__`
  row in `dpd_fields_classes.py`.
- **3 rows still read `on_change`** — `dpd_fields.py:153`, `:199` and `:337`.
  These are correct and must not be "fixed". `on_change` there is the
  *wrapper's* parameter name, shared with `FieldConfig.on_change` across all 48
  field definitions; the wrapper forwards it to `super().__init__(on_select=)`.
  Renaming it is a cosmetic rename, out of scope per AD#8.

The plan's own Phase 7 prose said "8 direct sites **plus** the wrapper", i.e. 9.
That was an off-by-one; the inventory says 7 direct plus the wrapper. Corrected
in `plan.md` from this measurement.

## What this does and does not prove

It proves no handler was silently dropped or rebound during the migration —
the failure mode where a button keeps rendering and quietly does nothing.

It does not prove any handler still *works*. Binding is a static fact; the
silent-failure items (BR-4's scroll, BR-14's Ctrl+S path, BR-18's Ctrl+Q,
BR-21's focus) all bind correctly while broken. Those need the running app.

Line numbers are stripped before comparing. Every file in scope moved lines
during the migration, so a line-sensitive diff would be 100% noise.
